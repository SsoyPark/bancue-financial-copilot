# BANCUE

근거 기반 은행 상담사 Copilot의 로컬 MVP입니다.

## 실행

### API

```bash
cd apps/api
python -m pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

### Web

```bash
cd apps/web
npm install
npm run dev
```

웹은 `http://localhost:5173`, API 문서는 `http://localhost:8000/docs`에서 확인합니다.

## AI Hub JSON 연결

기본 실행에서는 `apps/api/data/sample`의 합성 JSON을 읽습니다. 실제 데이터 폴더를
연결할 때는 API 실행 전에 환경변수를 지정합니다.

### Windows 명령 프롬프트

```bat
set BANCUE_DATA_DIR=C:\데이터\은행_JSON_폴더
set BANCUE_DATA_LIMIT=200
python -m uvicorn app.main:app --reload --port 8000
```

원본 폴더는 읽기만 하며 프로젝트나 GitHub에 복사하지 않습니다. 현재 단계에서는
위험도와 공식 근거가 아직 계산되지 않았으므로 JSON에서 읽은 상담을 `Unknown`과
`Received` 상태로 변환한 뒤, 설명 가능한 키워드 규칙 v1을 적용합니다. 화면의
`판정 이유`와 `RISK-*` 규칙 ID에서 어떤 규칙이 적용됐는지 확인할 수 있습니다.

## 개인정보 마스킹

API는 위험도 분석과 화면 응답 전에 상담 텍스트의 전화번호, 이메일,
주민등록번호, 계좌번호를 정규식 규칙 v1으로 마스킹합니다. 원문 대신 `[전화번호]`,
`[이메일]`, `[주민등록번호]`, `[계좌번호]` 자리표시자가 전달됩니다. 상담 상세 화면의
`개인정보 마스킹 완료` 영역에서 감지된 유형을 확인할 수 있습니다.

현재 규칙은 포트폴리오용 기준선입니다. 실제 운영 단계에서는 암호화된 원문 저장소,
권한 제어, 접근 로그와 함께 오탐·미탐 평가가 추가로 필요합니다.

## 공식 공개자료 기반 근거 문서

`apps/api/data/knowledge`에는 공식 공개자료를 상담 검색용으로 짧게 요약한 근거 5개가
있습니다. 원문 전체를 복사한 내부 업무지침이 아니라 공개된 소비자 안내·약관·정책·
행정규칙을 바탕으로 만든 포트폴리오용 요약입니다.

- 금융결제원: 자동이체 조회·해지·출금계좌 변경
- 여신금융협회: 카드 분실·도난 신고 및 부정사용 확인
- 우리은행: 만기자금 자동재예치 특약
- 금융위원회: 중도상환수수료 제도 개편
- 국가법령정보센터: 외국환거래 확인 의무

각 JSON에는 `source_organization`, `source_url`, `source_published_at`, `verified_at`,
`review_status`, `summary_method`가 저장됩니다. 공식 자료인데 HTTPS 원문 URL·기관·
확인일이 없으면 로더가 해당 파일을 제외하며, `Review Required` 상태인 문서는 검색
결과와 답변 초안에 사용하지 않습니다.

웹의 `지식 관리` 메뉴에서 5개 근거의 제공 기관, 기준일, 확인일, 검증 상태와 공식
원문 링크를 확인할 수 있습니다. 상담 상세 화면에서도 사용된 근거의 원문을 바로 열 수
있습니다. API는 마스킹과 위험도 분석을 마친 상담의 주제·요약·질문·의도에서 문서
키워드를 찾고 점수를 더해 관련 문서를 정렬합니다.

검색 API는 다음 주소에서 직접 시험할 수 있습니다.

```text
http://localhost:8000/api/knowledge/search?q=자동이체%20조회
http://localhost:8000/api/knowledge/sources
```

별도의 지식 문서 폴더를 연결할 때는 `BANCUE_KNOWLEDGE_DIR` 환경변수를 사용합니다.
검색 v2는 `apps/api/app/query.py`의 설명 가능한 규칙으로 일상 표현을 금융 용어로
확장한 뒤 기존 키워드 점수를 계산합니다. 예를 들어 `매달 빠져나가는 금액`과
`다른 통장`이 함께 나타나면 `자동이체·자동납부·출금계좌·변경`을 검색용 질의에만
추가합니다. 고객의 원문은 수정하지 않으며, 적용된 `QUERY-*` 규칙 ID와 확장 용어를
API 및 화면에 함께 표시합니다.

현재 방식은 작은 합성 데이터에서 동작을 설명하기 위한 규칙 기반 MVP입니다. 실제
서비스에서는 더 큰 독립 평가셋으로 과도한 확장과 누락을 검사하고, 임베딩 검색과
키워드 검색을 결합한 하이브리드 검색으로 확장해야 합니다.

### 검색 판단 설명

`지식 관리` 화면의 `검색 판단 확인`에서 질문을 직접 입력하면 다음 정보를 함께
확인할 수 있습니다.

- 고객이 입력한 원본 질문과 규칙으로 확장된 검색 질의
- 적용된 `QUERY-*` 규칙과 추가된 금융 용어
- 일치한 문서 후보, 키워드, 후보별 규칙 점수
- 최소 기준 8점 통과 여부와 근거 연결·검색 중단 이유

예를 들어 `자동이체 조회`는 관련 표현이 충분해 근거 문서가 연결됩니다. 반면
`해외송금 회사에 취업하려면 어떤 자격증이 필요한가요?`는 금융 용어가 하나 들어가도
후보 점수가 8점에 미달하므로 답변 근거로 사용하지 않습니다. 상담 상세의 `AI 분석`
영역에도 실제 상담 검색에 사용한 같은 판단 기록이 표시됩니다.

```text
http://localhost:8000/api/knowledge/explain?q=자동이체%20조회
```

여기에 표시되는 점수는 키워드 일치 규칙을 설명하기 위한 점수이며, 정답일 확률이나
통계적 신뢰도 퍼센트가 아닙니다. 실제 운영에서는 검색 로그에 개인정보가 남지 않도록
접근 권한과 보관 기간도 별도로 관리해야 합니다.

## 근거 기반 답변 초안

검증된 근거 문서가 있을 때만 템플릿 초안을 생성합니다. 초안에는 사용된 문서의
제목·조항·내용, 필수 확인 항목과 문서 ID가 포함됩니다. 근거가 없으면 원천 상담
데이터에 답변이 있어도 초안을 비우고 승인을 차단합니다. `Critical`과 `High` 상담은
초안이 생성되어도 관리자 검토가 필요합니다.

현재 초안은 외부 LLM을 사용하지 않으며 공식 공개자료의 요약을 템플릿에 넣습니다.
원문과 고객의 실제 계약 조건이 우선이므로 상담사가 이를 확인하기 전에는 최종 안내로
사용할 수 없습니다.

## 상담 처리 워크플로

상세 화면의 필수 확인 항목을 모두 체크하면 `Low`와 `Medium` 상담의 초안을 승인할
수 있습니다. `Critical`과 `High` 상담은 승인할 수 없고 관리자 이관이 필요합니다.
반려는 상담을 `Needs Info`, 이관은 `Escalated`, 승인은 `Completed` 상태로 변경합니다.
각 처리에는 담당자, 처리 시각, 메모와 확인 항목이 기록됩니다.

## 상담사 피드백 루프

상담 상세의 `품질 피드백` 탭에서 `의도 파악 정확도`와 `답변 초안 정확도`를 각각
1~5점으로 평가합니다. 두 항목 중 하나라도 3점 이하이면 다음 개선 사유를 함께
선택해야 합니다.

- 잘못된 근거
- 근거 부족
- 초안 품질

피드백은 상담 ID, 두 항목 점수, 개선 사유, 담당자, 시각과 선택 입력 비고를 SQLite에
추가합니다. 고객의 상담 원문이나 답변 초안 전체를 중복 저장하지 않습니다. 메모에
전화번호·이메일·주민등록번호·라벨이 있는 계좌번호가 들어오면 기존 개인정보 규칙으로
마스킹한 뒤 저장합니다.

`품질 관리` 화면에서는 의도 파악 평균점수, 답변 초안 평균점수, 개선 필요 건수,
사유별 건수와 최근 기록을 확인할 수 있습니다. 정답셋 평가는 배포 전 검색 품질을
확인하고, 상담사 피드백은 실제 사용 중 발견되는 문제를 다음 평가 케이스로 전환하기
위한 자료입니다.

상담 상세의 정보 밀도를 낮추기 위해 `답변 검토`와 `품질 피드백`을 탭으로 분리하고,
근거 문서·검색 판단·처리 이력은 필요할 때만 펼쳐보는 구조로 표시합니다.

```text
POST http://localhost:8000/api/consultations/{consultation_id}/feedback
GET  http://localhost:8000/api/feedback/summary
```

현재 로컬 MVP는 사용자가 입력한 피드백을 그대로 품질 개선용으로 집계합니다. 실제
운영에서는 역할 기반 접근 제어, 메모 보관 기간, 삭제 정책과 감사 로그를 추가해야 합니다.

## SQLite 영구 저장

상담의 처리 상태, 승인·반려·이관 이력과 상담사 품질 피드백은 Python 기본
`sqlite3`를 사용해 다음 파일에 저장합니다.

```text
apps/api/data/runtime/bancue.db
```

서버 시작 시 원천 상담 JSON을 다시 분석한 뒤, 상담 ID가 일치하는 저장 상태와 처리
이력을 복원합니다. 상담 원문과 생성된 초안 전체를 중복 저장하지 않고 변경되는
워크플로 상태만 저장합니다. DB 파일은 `.gitignore`에 포함되어 Git에 올라가지 않습니다.

다른 위치를 사용하려면 API 실행 전에 `BANCUE_STATE_DB` 환경변수를 지정할 수
있습니다. 저장 상태를 처음부터 다시 시험하려면 서버를 종료한 뒤 `bancue.db` 파일을
다른 백업 폴더로 이동하고 서버를 다시 실행하면 새 DB가 생성됩니다.

## RAG 검색 품질 평가

`apps/api/data/evaluation/retrieval_cases.json`에는 정답 문서 ID가 지정된 검색 정답셋
10개와 검색하면 안 되는 범위 밖 질문 5개가 있습니다. 평가 API는 각 질문에 대해
상위 3개 문서를 검색하고 다음 지표를 계산합니다.

- `Recall@1`: 첫 번째 검색 결과가 정답인 비율
- `Recall@3`: 상위 3개 검색 결과 안에 정답이 있는 비율
- `MRR`: 정답 문서 순위의 역수를 평균한 값
- `No-answer accuracy`: 근거가 없는 질문에서 올바르게 검색을 멈춘 비율
- `Overall accuracy`: 정답 검색과 올바른 무응답을 모두 포함한 전체 성공률

키워드 검색 v1 기준선은 정답 질문에서 `Recall@1 0.90`이지만 범위 밖 질문 5개를
모두 오검색하여 전체 정확도는 `0.60`입니다. 개선 검색은 질의 확장과 최소 검색 점수
8점 게이트를 함께 적용합니다. 관련 키워드 하나만 우연히 포함된 5~7점 결과는 답변
근거로 사용하지 않습니다. 개선 후 `Recall@1`, `No-answer accuracy`, `Overall
accuracy`가 각각 `1.00`입니다.

`해외송금`과 그 안에 포함된 `송금`처럼 같은 의미가 겹치는 키워드는 가장 구체적인
표현 하나만 점수에 반영합니다. 이 규칙으로 단순히 금융 용어가 들어간 취업·개발·
광고 문구 질문을 상담 근거로 잘못 연결하는 문제를 줄입니다.

웹의 `품질 관리` 메뉴에서는 기존 전체 정확도 60%, 개선 전체 정확도 100%, 무응답
정확도 100%와 오검색 0건을 확인합니다. RET-010은 `기존 실패 → 개선 1위`,
NEG-001~005는 `기존 오검색 → 개선 무응답`으로 표시됩니다. 다음 API는 개선 결과와
전·후 비교 결과를 각각 반환합니다.

```text
http://localhost:8000/api/evaluation/retrieval
http://localhost:8000/api/evaluation/retrieval/comparison
```

여기서 100%는 공식 공개자료 요약 5개와 정답셋 15개에 한정된 결과이며 실제 금융 상담 전체의
성능을 뜻하지 않습니다. 이후 실제 공개 문서와 별도 검증셋으로 다시 측정해야 합니다.

## 테스트

API 폴더에서 가상환경을 활성화한 뒤 실행합니다.

```bat
python -m pytest -q
```

`pytest.ini`가 `app` 폴더를 Python 모듈 경로에 포함하므로 Windows에서도 같은
명령으로 테스트할 수 있습니다.

단위 테스트뿐 아니라 다음 사용자 흐름을 묶은 통합 테스트도 포함합니다.

- 일반 상담 조회 → 근거·초안 확인 → 1~5점 피드백 저장 → 품질 집계
- 고위험 상담 조회 → 승인 차단 → 관리자 이관
- 관련 질문 근거 연결 → 범위 밖 질문 검색 중단 → 검색 평가 지표 확인

면접이나 포트폴리오 시연 순서는 [`docs/DEMO.md`](docs/DEMO.md)에 5분 분량으로
정리되어 있습니다.
